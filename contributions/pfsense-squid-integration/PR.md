# [pfSense] Parse OPNsense Squid access logs (ECS-JSON)

## Proposed commit message

**WHAT:** Adds a conditional JSON branch to the Squid ingest pipeline. When `message` starts
with `{`, it is decoded into a temporary field and the values are renamed onto the same fields
the existing grok branch produces (`url.original`, `http.request.method`,
`http.response.status_code`, `http.response.bytes`, `http.version`, `source.address`,
`squid.request_status`, `squid.hierarchy_status`). The grok branch is now guarded so it only
runs for non-JSON input. Downstream processors (`uri_parts`, `convert`, `event.category`,
`event.outcome`) are unchanged and shared by both formats. Also recovers `url.domain`/`url.port`
for `CONNECT` requests, where the authority form (`host:443`) has no scheme for `uri_parts` to
split.

**WHY:** The `pfsense` integration is used for OPNsense as well as pfSense, and works for every
other provider. OPNsense emits Squid access logs as ECS-JSON (`logformat opnsense`), which the
classic-text grok pattern cannot parse, so every Squid event lands unparsed with
`event.kind: pipeline_error`. Operators cannot work around it: both values of the OPNsense GUI
*target* setting generate the identical `access_log syslog:local4.info opnsense` directive, and
`squid.conf` is regenerated by `configctl`, so classic format is not selectable. Squid is
frequently the only source that records the true destination of proxied traffic, so the gap
removes proxy visibility entirely — silently, since ingest volume looks normal.

### Why not `add_to_root`

The OPNsense payload contains its own `event` object. Merging it to root overwrites
`event.provider`, and `default.yml` routes on `ctx.event.provider == 'squid'` with a `drop`
processor for anything outside the provider allowlist — so `add_to_root` causes documents to be
**silently dropped**. This was observed in practice before switching to `target_field`. Worth
keeping the comment in the pipeline so it is not reintroduced.

### Evidence — no regression on the classic path

Both pipelines (current `main` and this PR) were run through `_ingest/pipeline/_simulate`
against the **existing** `test-pfsense-squid.log` fixtures on a 9.5.0 cluster, and the
resulting `_source` documents compared field by field:

| Input | Result |
|---|---|
| `TCP_MISS/304 … GET https://github.com/…` | **byte-identical** |
| `TCP_MISS/304 … CONNECT github.com:443` | **byte-identical** |

## Compatibility

| User | Effect |
|---|---|
| pfSense, classic Squid text | **No change** — `message` is not JSON, branch is skipped, grok runs as before |
| OPNsense, no workaround | Previously unparsed; now populates ECS fields. Strictly additive |
| OPNsense with a local workaround | Should remove custom pipelines that write to a `squid.*` namespace, to avoid duplicate mappings |

Two behavioural changes worth noting for anyone monitoring ingest health: for OPNsense Squid
events, `event.kind: pipeline_error` and `tags: ["preserve_original_event"]` will **stop**
being set, because the events now parse successfully.
